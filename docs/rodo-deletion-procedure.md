# Процедура видалення даних за запитом (RODO / право на забуття)

Останнє оновлення: 2026-08-04. Описує, що робить існуючий код зараз, і що персонал
має перевірити вручну — це не абстрактна політика, а робоча інструкція під поточний стан репозиторію.

## Коли застосовується

Клієнт (лід, учасник, кандидат) письмово вимагає видалення своїх персональних даних
(email, Telegram, форма на сайті, дзвінок — зафіксувати канал звернення).

## Що вже автоматизовано

`POST /api/admin/rodo` (UI: `/admin/rodo`, `/admin/gdpr`) → `purgeUserData()` у `lib/rodo.ts`.
Доступ лише для ролі `admin`. При виклику з `userId`:

1. Пише запис `request_deletion` у `kompas_rodo_consent_logs` (email/phone/IP/user-agent —
   **до** анонімізації, щоб лишився доказ, що запит виконано).
2. `kompas_users`: `full_name` → `Deleted User`, `email` → `deleted_user_<id>_<ts>@kompasmigracji.com`,
   `phone` → NULL, `password_hash` → `PURGED_GDPR`, `status` → `deleted`.
3. `kompas_member_profiles`: `notes` → `"Profile purged on request (RODO)"`, `dues_status` → `purged`.
4. `leads` з тим самим email/phone: ім'я/контакти замінюються на `Purged...`, `deleted_at` = now,
   `status` = `closed`.

Це **не фізичне видалення рядків** — навмисна анонімізація (soft), щоб зберегти
статистику/аналітику без ідентифікації особи.

## Що НЕ робить поточний код — перевіряти вручну

- **`kompas_rodo_consent_logs` сам по собі не анонімізується** — у ньому лишається
  оригінальний email/phone, зафіксовані на момент запиту (це навмисно, як доказ виконання
  запиту; але якщо клієнт вимагає видалення *повністю*, обговоріть з юристом, чи цей
  запис підпадає під виняток "доказ виконання правового обов'язку").
- **Файли в Supabase Storage не видаляються** — на сьогодні жоден код у репозиторії не
  завантажує файли через `storage.from(...)` (бакет документів існує й захищений
  політиками, але `case_documents`/завантаження документів клієнтом ще нікуди не
  підключені — див. нижче). Коли цю функціональність підключать, `purgeUserData()`
  доведеться розширити видаленням об'єктів з бакета, інакше файли переживуть "видалення".
- **`immigration_cases`, `case_documents`, `case_billing`, `case_activities` не
  зачіпаються** — ці таблиці мають коректні RLS-політики, але жоден маршрут додатку їх
  не читає й не пише (перевірено `grep` по `app/`, `lib/` — нуль збігів). Поки що це не
  проблема для RODO (даних там немає), але як тільки цей модуль підключать до реального
  UI, його теж треба буде додати в `purgeUserData()`.
- **Чат-повідомлення** (`crm-chats`/Telegram-історія в `leads.history`) — поле `history`
  у `leads` не очищається окремо; воно замінюється лише опосередковано, якщо сам рядок
  ліда підпадає під анонімізацію вище. Перевірте вручну, чи потрібно очищати `history`.
- **Фактури / бухгалтерські записи не чіпаються** — це навмисно: рахунки-фактури
  зберігаються 5 років за законом незалежно від запиту на видалення (KSeF/бухгалтерський
  облік). Не видаляйте й не анонімізуйте фінансові документи за запитом RODO.
- **`kompas_audit_log`** — лишається недоторканим навмисно: журнал доступу потрібен,
  щоб відповісти на власне питання "хто бачив мої дані" і як доказ дотримання процедур.

## Покрокова інструкція для персоналу

1. Отримати й задокументувати запит (дата, канал, ім'я/контакт клієнта, хто прийняв).
2. Знайти `userId` клієнта в `/admin/members` або `/admin/leads`.
3. Виконати `POST /api/admin/rodo` з `{ "userId": <id> }` через `/admin/rodo` UI.
4. Перевірити `kompas_rodo_consent_logs` — рядок `request_deletion` з'явився.
5. Вручну перевірити пункти вище (файли в Storage, `history`, будь-які інші таблиці
   з email/phone цього клієнта, яких скрипт не знає — наприклад майбутні модулі).
6. Підтвердити клієнту виконання запиту письмово, зберегти копію підтвердження.
7. Зробити позначку в CRM (нотатка/активність), що запит закрито, з посиланням на
   запис у `kompas_rodo_consent_logs`.

## RTO для запиту на видалення

RODO вимагає відповіді протягом 1 місяця (можна продовжити ще на 2 місяці для складних
випадків із письмовим поясненням клієнту). Технічне виконання кроків 3-5 займає хвилини —
головний час йде на крок 1 (підтвердження особи запитувача) і крок 5 (ручна перевірка).
